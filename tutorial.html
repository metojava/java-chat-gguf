gguf-chat — how the Java GGUF loader works

de.kherud:llama 4.2.0 · JNI bindings over llama.cpp / GGML · annotated walkthrough, verified on this machine

Read this firstThe project in this folder builds and runs, but produces wrong answers. Asking it “Write a Java method to reverse a string” returns “It seems like you want me to write something, but I'm not sure what you're asking…” — the model never sees your question. The cause is a single missing token. See section 5 for the diagnosis and the one-line fix.

1. What this project is

A Maven command-line chat application that runs a GGUF model locally in Java. It does not reimplement inference — it calls llama.cpp through JNI.

LayerWhat it is
GgufChat.javaYour code: CLI parsing, REPL, prompt building, history
de.kherud:llama 4.2.0Java API + JNI glue (LlamaModel, ModelParameters, InferenceParameters)
jllama.dllNative bridge, extracted from the JAR to %TEMP% at first use
llama.cpp / GGMLCompiled into the DLL. This JAR bundles build 4916, MSVC x64
.gguf fileQuantized weights, memory-mapped by GGML

Two different libraries, easily confused llama4j.com documents com.llama4j:gguf, a pure-Java library for reading and writing GGUF files — metadata, tensor descriptors, offsets. It does not run inference. This project uses de.kherud:llama, which does run inference via JNI. They solve different problems and can be used together: llama4j to inspect a model's metadata (quant type, context length, chat template) without loading gigabytes, de.kherud to actually generate text.

2. Execution flow

main()
 └─ Cli.parse(args)            plain switch over --flags, no dependency
     └─ resolveModel()          --model, else ./Llama-3.2-3B-Instruct-Q4_K_M.gguf
         └─ LlamaModel.setLogger()  silence GGML unless --verbose
             └─ new LlamaModel(mp)   JNI: loads DLL, mmaps weights, builds ctx
                 ├─ runOneShot()      --prompt: answer once, exit
                 └─ runRepl()         interactive loop
                     └─ generate()
                         ├─ buildLlamaChatPrompt()  history → Llama-3 markup
                         ├─ new InferenceParameters()
                         └─ for (LlamaOutput o : model.generate(ip))
                                              blocking iterator, one chunk per token

The try (LlamaModel model = ...) block matters: LlamaModel is AutoCloseable and holds native memory the JVM garbage collector cannot see. Leaving the block frees the model. Note also the deliberate System.exit(0) in main's finally — the native layer starts non-daemon threads that otherwise keep the JVM alive after the chat ends.

3. The three API objects

ModelParameters — fixed at load time

ModelParameters mp = new ModelParameters()
        .setModel(modelPath.toAbsolutePath().toString())
        .setCtxSize(cli.ctxSize)      // 4096 default
        .setThreads(cli.threads)      // cores/2 default
        .setGpuLayers(cli.gpuLayers); // 0 = pure CPU

These cannot change without reloading the model — which is why /ctx in the REPL only prints a message telling you to restart.

InferenceParameters — per request

InferenceParameters ip = new InferenceParameters(prompt)
        .setTemperature(cli.temperature)
        .setTopP(cli.topP)
        .setTopK(cli.topK)
        .setRepeatPenalty(cli.repeatPenalty)
        .setNPredict(cli.maxTokens)
        .setStopStrings("<|start_header_id|>", "<|eot_id|>")
        .setSeed(cli.seed);

LlamaOutput — streaming

for (LlamaOutput out : model.generate(ip)) {
    System.out.print(out.text);   // arrives incrementally
    System.out.flush();
    tokenCount++;
}

model.generate() returns an Iterable; each step blocks until the native side produces the next chunk. That is what makes the typewriter effect work.

tok/s here is approximatetokenCount counts iterations, not tokens. A chunk usually maps to one token but is not guaranteed to, and the timer includes prompt processing. Treat the printed figure as indicative.

4. Prompt construction

Chat models are trained on a strict markup. Llama-3 uses header blocks; the code builds them by hand:

private static String buildLlamaChatPrompt(String system, Deque<Message> turns) {
    StringBuilder sb = new StringBuilder();
    if (system != null && !system.isBlank()) {
        sb.append("<|start_header_id|>system<|end_header_id|>\n\n")
          .append(system.trim()).append("<|eot_id|>");
    }
    for (Message m : turns) {
        sb.append("<|start_header_id|>").append(m.role())
          .append("<|end_header_id|>\n\n")
          .append(m.content()).append("<|eot_id|>");
    }
    sb.append("<|start_header_id|>assistant<|end_header_id|>\n\n");
    return sb.toString();
}

The whole history deque is replayed every turn, which is how the model gets conversational memory — and why long chats get slower and eventually overflow --ctx.

5. The bug: a missing BOS token

SymptomThe model answers as if the question were empty.

ai> It seems like you want me to write something, but I'm not sure what you're
    asking me to write yet! Could you please provide more context...
   [64 tokens, 3.88 s, 16.51 tok/s]

Diagnosis

The Javadoc at line 256 states:

* The tokenizer adds the leading BOS (<|begin_of_text|>) automatically,
 * so we don't prepend it.

That assumption is false for this binding. When a prompt is supplied as a raw string via new InferenceParameters(prompt), it is tokenized without add_special, so no <|begin_of_text|> (id 128000) is prepended. Llama-3 was trained with BOS always present; without it the header markup is interpreted as stray text and the actual question is effectively ignored.

Proved by testing the identical prompt with the token added:

PromptResult
Without <|begin_of_text|>“I'm not sure what you're asking me to write…”
With <|begin_of_text|>Correct StringReverser class with a working reverse() method

Fix B — let the binding apply the model's own template

More portable: works for Qwen/ChatML and other families without hand-writing markup. Uses the chat_template stored in the GGUF metadata.

List<Pair<String,String>> msgs = new ArrayList<>();
for (Message m : history) msgs.add(new Pair<>(m.role(), m.content()));

InferenceParameters ip = new InferenceParameters("")
        .setMessages(systemPrompt, msgs)
        .setUseChatTemplate(true)
        .setTemperature(cli.temperature)
        .setNPredict(cli.maxTokens);

Caveat found in testingOn this exact version (4.2.0 + bundled build 4916) the setMessages path also misbehaved in a quick test, emitting unrelated text. Fix A is verified working here; Fix B is the cleaner design but verify it on your setup before relying on it.

Also worth removing

.setStopStrings("<|start_header_id|>", "<|eot_id|>")

<|eot_id|> is this model's EOS token (id 128009) and already ends generation natively. Matching it as a string is redundant and forces extra per-token substring scanning.

6. Performance — what actually matters

The governing constraintGenerating one token requires reading every weight in the model from RAM; each is used for a single multiply-add and discarded. Speed is memory bandwidth ÷ model size and almost nothing else. Measured on this machine: a bare 4 GB read loop reaches 24.9 GB/s, and llama.cpp reaches 24.4 GB/s while also doing the arithmetic — 98% of the hardware ceiling. No Java-side tuning can beat physics.

Ranked by real impact

1. Thread count — the one setting that matters

The default is cores / 2 = 4 here, which leaves performance on the table.

--threads 6    # best for a 1B model on this machine
--threads 8    # best for a 7B model
ThreadsLlama-3.2-1B (0.75 GB)Qwen2.5-Coder-7B (4.36 GB)
4 (this project's default)23.7 t/s4.67 t/s
626.3 t/s5.12 t/s
826.4 t/s5.59 t/s

A small model plateaus early because it partly fits in cache; a large one stays bandwidth-starved and uses every thread. Consider changing the default:

int threads = Math.max(1, Runtime.getRuntime().availableProcessors() / 2);
int threads = Math.max(1, Runtime.getRuntime().availableProcessors() - 2);

2. Context size — free memory savings

--ctx 4096 is the default; the KV cache grows linearly with it and is allocated up front whether used or not. For short Q&A, --ctx 2048 halves that with no downside.

3. Prune the history you resend

Every turn re-sends the entire conversation, so prompt-processing cost grows without bound. Cap it:

private static final int MAX_TURNS = 8;
while (history.size() > MAX_TURNS) history.removeFirst();

Or use /reset between unrelated questions — the single most effective habit for keeping a long session fast.

4. Sampling settings — negligible for speed

--temp, --top-p, --top-k, --repeat-penalty affect output quality, not throughput; sampling is microseconds against a ~180 ms per-token memory cost. Use --temp 0 for deterministic code generation, not for speed.

5. JVM flags — almost irrelevant

The weights live in native memory, not the Java heap, so -Xmx tuning does nothing for inference. The only worthwhile flag avoids a brief startup stall:

java -XX:+AlwaysPreTouch -cp ... com.jm.ggufchat.GgufChat

6. GPU offload — not available here

warning: no usable GPU found, --gpu-layers option will be ignored
warning: one possible reason is that llama.cpp was compiled without GPU support

The bundled jllama.dll is a CPU-only build, so --gpu-layers is silently ignored regardless of hardware.

7. Things that do not help

IdeaReality
More RAM capacityBandwidth matters, not capacity. The 7B already fits in 13.9 GB.
Requantizing Q4_K_M → Q3_K_MTested: −19% size gave only +8% speed (4.61 → 4.98 t/s). Q3_K blocks cost more CPU to unpack.
A different inference enginellama.cpp is already at 98% of the memory ceiling.
Trees / indexes over weightsDense models use every weight in fixed order — there is nothing to search, and pointer chasing would destroy SIMD and prefetch.

8. The genuinely large wins

  1. Enable XMP/DOCP in the BIOS — free, up to +33%. Both DIMMs are rated 3200 MT/s but run at 2400. A bandwidth-bound workload scales almost linearly with memory clock.
  2. Use a smaller model. The 1B is ~4.7× faster than the 7B; switch only when needed.
  3. Speculative decoding (2–3×). A small draft model proposes several tokens which the large model verifies in one pass over its weights — same bytes moved, several tokens produced, identical output. Supported by llama.cpp, though not exposed by this Java binding.

8. Inspecting a model with llama4j (no loading required)

The separate com.llama4j:gguf library reads GGUF headers without touching the weights — useful for discovering a model's chat template, context length and quantization before deciding how to prompt it.

<dependency>
    <groupId>com.llama4j</groupId>
    <artifactId>gguf</artifactId>
    <version>0.1.1</version>
</dependency>
import com.llama4j.gguf.GGUF;

GGUF gguf = GGUF.read(Path.of("Llama-3.2-1B-Instruct-Q4_K_M.gguf"));

// the template this model actually expects
String tmpl = gguf.getValue(String.class, "tokenizer.chat_template");

// context length it was trained for
int ctx = gguf.getValueOrDefault(int.class, "llama.context_length", 4096);

// BOS / EOS ids - exactly the values involved in the bug above
int bos = gguf.getValue(int.class, "tokenizer.ggml.bos_token_id"); // 128000
int eos = gguf.getValue(int.class, "tokenizer.ggml.eos_token_id"); // 128009

It can even read metadata straight from Hugging Face over HTTP, without downloading the file:

static GGUF readFromHuggingFace(String user, String repo, String file) throws IOException {
    URL url = new URL("https://hf.co/%s/%s/resolve/main/%s".formatted(user, repo, file));
    try (var ch = Channels.newChannel(
             new BufferedInputStream(url.openConnection().getInputStream()))) {
        return GGUF.read(ch);
    }
}

A practical use: read tokenizer.chat_template at startup and pick the right prompt builder automatically, instead of hardcoding Llama-3 markup.

9. Troubleshooting

SymptomCause & fix
Model replies as if the prompt were empty Missing <|begin_of_text|>. Apply Fix A in section 5.
Rambling or role-confused output on a non-Llama model Wrong chat template. Qwen needs ChatML. Use Fix B or branch per family.
Model file not found Default is ./Llama-3.2-3B-Instruct-Q4_K_M.gguf relative to the working directory. Pass --model with an absolute path.
warning: no usable GPU found Expected — the bundled DLL is CPU-only. --gpu-layers is ignored.
JVM hangs after the chat ends Native non-daemon threads. Already handled by System.exit(0) in main.
Generation slows down over a long chat The whole history is resent each turn. Use /reset or cap history.
Reply truncated mid-sentence Hit --max-tokens (default 1024). Raise it.
Slow first run jllama.dll is extracted to %TEMP% once, plus OS page-cache warm-up.
Maven cannot resolve de.kherud:llama First build needs network access; it downloads ~40 MB including the native DLL.

10. Summary of suggested changes

  1. Add <|begin_of_text|> to buildLlamaChatPrompt() — without it the program does not work at all.
  2. Change the default thread count from cores/2 to cores-2 — roughly +11% for free.
  3. Drop setStopStrings — <|eot_id|> is already the EOS token.
  4. Lower the default --ctx to 2048 for short sessions; it halves KV-cache memory.
  5. Cap conversation history so prompt cost stops growing without bound.
  6. Detect the chat template from GGUF metadata (llama4j, or Fix B) instead of hardcoding Llama-3.
  7. Fix the tok/s counter to measure generation only, excluding prompt processing.
